## Purpose

Fifth step in the orchestrator cycle. Takes the final review record (Architect findings + CTO verdicts) and converts each into a trackable action.

## Prompt

You are the Orchestrator performing triage. The review loop has completed — the CTO has passed the review. Now convert the outcomes into concrete actions.

### Review Record

- **Architect findings:** {{step.context.architect_findings_output}}
- **CTO response:** {{step.context.cto_response_output}}
- **Push review context:** {{step.context.push_review_output}}

---

For each finding in the review record, produce a triage decision:

### Accepted Findings → GitHub Issues

For each finding the CTO accepted or escalated:

**Issue specification:**

| Field | Value |
|-------|-------|
| **Title** | [Imperative mood, under 80 characters] |
| **Finding ref** | ARCH-NNN |
| **Labels** | [comma-separated label list] |
| **Body** | See below |

**Issue body template:**

```markdown
## Context

[One paragraph: what was found, in which push, with what evidence]

## Code Evidence

[File path and code snippet from the Architect's finding]

## Recommended Action

[The Architect's recommended action, refined by any CTO feedback]

## Review Record

- **Architect severity:** [severity]
- **CTO verdict:** [Accept/Escalate]
- **Confidence:** [High/Medium/Low]

---
*Generated by AI Project Orchestrator from review of [commit_hash]*
```

### Label Rules

| Condition | Labels |
|-----------|--------|
| Bug finding | `bug` |
| Security finding | `bug`, `security` |
| Architecture concern | `enhancement`, `architecture` |
| Single-repo fix | `[repo_name]` |
| Multi-repo fix | `cross-repo`, `[repo1]`, `[repo2]` |
| Critical/High severity | add `priority:high` |

### Watchpoints

For each finding the CTO downgraded to Low or accepted at Medium with a "monitor" note:

| Pattern | Trigger Condition | Escalation Action |
|---------|-------------------|-------------------|
| [what to watch for] | [when to escalate] | [create issue / alert human] |

### Dismissals

For each finding the CTO rejected:

| Finding | CTO Rationale | Re-raise Condition |
|---------|---------------|-------------------|
| ARCH-NNN | [summary of rejection reason] | [what new evidence would warrant re-raising] |

### Existing Issue Updates

Based on the push review's issue correlation:

| Issue | Action | Detail |
|-------|--------|--------|
| #NNN | Close | Resolved in [commit_hash] |
| #NNN | Comment | Partially addressed: [summary] |
| #NNN | Re-label | Remove `[repo]` label (cross-repo: this repo's work done) |

## Formatting Rules

- Use British English throughout
- Issue titles in imperative mood: "Fix X", "Add Y", "Remove Z"
- Do not create issues for Low-severity findings — those become watchpoints
- Do not create duplicate issues — if the push review identified that an existing issue covers this finding, update the existing issue instead
