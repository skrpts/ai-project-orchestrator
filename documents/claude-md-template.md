## Purpose

This template defines the structure for a repo's `CLAUDE.md` file — the persistent instruction set that every agent session reads first. It must be concise (~80 lines), comprehensive, and stable (changes infrequently).

## Template

```markdown
# [Project Name] — [One-Line Description]

## What Is This
[2-3 sentences: what this repo does, who uses it, how it fits in the larger system. No marketing language — just facts.]

## Project Mantra
> **"[Core design principle in one sentence]"**
> [One sentence explaining how this mantra guides decisions. Include permission to push back.]

## Session Protocol
1. Read `docs/BRIEFING.md` — this is your work order, generated by the orchestrator
2. Work the priority queue in order
3. Run tests for every code change (see Testing below)
4. **Commit your work as you go.** Atomic commits after each logical unit.
5. **Between priority items:** check the briefing for a `[compact]` marker. If marked, run `/compact` and re-read this file and `docs/BRIEFING.md`.
6. Before `git push`: write a summary to `.orchestrator-msg` (hook delivers it)
7. After fixing a GH Issue: comment with commit hash and close (or remove label for cross-repo)
8. **NEVER run `git push`** — the human pushes manually.

## Communication Protocol
- **[Language variant]** throughout all code, docs, and UI copy
- **No platitudes.** Direct answers only.
- **Challenge the human.** Push back on bad ideas, explain trade-offs honestly.

## Tech Stack
- **[Layer]:** [Technology + specific version if relevant]
- **[Layer]:** [Technology]
- **[Layer]:** [Technology]
- **Hosting:** [Platform] ([domain] — [status])

## Code Conventions
- [Language/style rule]
- [Naming convention]
- [Architecture principle]
- [Documentation rule]
- [Testing philosophy]

## Testing
- **[Test type]:** [When required and what to verify]
- **[Test type]:** [When required and what to verify]
- **Report results:** Include test outcomes in `.orchestrator-msg` push summary.

## Project Structure
[Tree showing key directories with 1-line descriptions]

## Context Budget — IMPORTANT
Your context window is expensive. Protect it.

**At session start, read ONLY:**
1. This `CLAUDE.md`
2. `docs/BRIEFING.md`
3. Files explicitly referenced in the briefing

**Do NOT read unless the current task requires it:**
- [Doc file] — only if [condition]
- [Doc file] — only if [condition]

**Rule: if the briefing doesn't mention it, don't load it.**

## GitHub Issues
Tracker: [repo/location]. Check open issues: [command]

Fix a single-repo issue: comment with hash, close it.
Fix your part of a cross-repo issue: comment, remove your label, do NOT close.
```

## Guidance Notes

### Length Discipline

The target is ~80 lines. Every section above is required, but keep each one tight:

- What Is This: 3 lines maximum
- Tech Stack: one line per technology, no descriptions
- Code Conventions: 5-7 bullet points, not paragraphs
- Project Structure: tree format, no prose

### What Does Not Belong in CLAUDE.md

- API documentation (put in architecture docs, referenced from briefing when needed)
- Decision history (put in decisions log)
- Session-specific instructions (put in BRIEFING.md)
- Deployment procedures (put in ops docs)
- Full testing instructions (put in a test guide, reference from CLAUDE.md)

### Update Frequency

CLAUDE.md should change infrequently — when the tech stack changes, conventions are updated, or the project structure shifts significantly. If you find yourself editing CLAUDE.md every session, the content probably belongs in BRIEFING.md instead.
