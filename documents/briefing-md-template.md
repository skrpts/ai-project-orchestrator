## Purpose

This template defines the structure for a repo's `BRIEFING.md` file — the session-specific work order generated by the orchestrator before each agent session. It is the second file the agent reads, after `CLAUDE.md`.

## Template

```markdown
# Briefing — [Repo Name]
**Date:** [YYYY-MM-DD]
**Session ref:** [orchestrator-session-id]

## Priority Queue

1. **GH#[NNN]** — [Imperative one-liner describing the task]
   - Read: `[specific/file/path.ext]` [optionally: lines NN-MM]
   - Done when: [concrete, verifiable acceptance criterion]
   [compact]

2. **GH#[NNN]** — [Imperative one-liner]
   - Read: `[specific/file/path.ext]`
   - Done when: [acceptance criterion]

3. **[Internal]** — [Imperative one-liner for non-issue tasks]
   - Read: `[file/path.ext]`
   - Done when: [acceptance criterion]

## Recently Completed

- `[7-char hash]` — [One-line summary of what was done]
- `[7-char hash]` — [One-line summary]
- `[7-char hash]` — [One-line summary]

## Cross-Repo Context

- **[Sibling repo]:** [Fact] — [why it matters to this repo]
- **[Sibling repo]:** [Fact] — [implication for current work]

## Constraints

- [Active constraint: deployment freeze, blocked dependency, known broken state]
- [Time-sensitive condition with deadline if applicable]
```

## Section Rules

### Priority Queue

- **Maximum 7 items.** If there are more, the orchestrator must prioritize. Agents should not face a wall of 15 tasks.
- **Every item has a context pointer.** No exceptions. `Read: docs/` is not a pointer. `Read: src/lib/auth.ts lines 42-68` is.
- **Every item has acceptance criteria.** "Done when: it works" is not acceptable. "Done when: the `/api/submit` endpoint returns 200 for valid payloads and 401 for missing auth headers" is.
- **Imperative mood.** "Fix the token refresh" not "The token refresh needs fixing".
- **Issue reference where possible.** Use `GH#NNN` for GitHub Issues, `[Internal]` for tasks that do not have an issue.

### Recently Completed

- **3-5 items maximum.** This is orientation context, not a changelog.
- **Most recent first.**
- **Include the commit hash** so the agent can reference the actual changes if needed.

### Cross-Repo Context

- **Only propagate actionable facts.** "App deployed v2.3" is not useful unless this repo needs to respond to that deployment.
- **One line per fact.** If it takes a paragraph to explain, it is too complex for the briefing — create an issue instead.
- **Bold the repo name** for quick scanning.

### Constraints

- **Only active constraints.** Remove expired freezes and resolved blockers.
- **Include deadlines** where applicable: "Deployment freeze until 2026-04-15" not just "Deployment freeze".
- **This section may be empty.** That is fine — do not invent constraints.

## Line Budget

The total BRIEFING.md must not exceed 60 lines. If content does not fit, cut in this order:

1. Constraints (least critical — agent can ask if blocked)
2. Cross-repo context (second least — agent can check sibling state if needed)
3. Recently completed (third — useful but not essential)
4. **Never cut priority items** — they are the entire point of the briefing

## Anti-Patterns

- **Preamble padding:** "Welcome to your session! Here's what we need you to do today." — wastes 2 lines.
- **Duplicate information:** Repeating something from CLAUDE.md. The agent reads both files.
- **Speculative tasks:** "If you have time, consider looking at..." — either it is a priority or it is not.
- **Vague scope:** "Improve the performance of the API" — which endpoint? What metric? What target?
